# Migration

Most codebases start with something: no policy at all, hand-written Polly policies, or
`AddStandardResilienceHandler`. This page moves each of them to this pipeline, one client at a time.

## From no policy

A plain `AddHttpClient` has one setting: `HttpClient.Timeout`, 100 seconds by default, for the whole call.

1. Add `.AddHttpResilience()`.
2. Decide the [attempt timeout](timeouts.md#attempt-timeout) from what the dependency normally takes,
   not from the old 100 seconds.
3. If callers relied on the call failing within some time, set `TotalTimeout` to that time. See
   [one timeout, as before](timeouts.md#one-timeout-as-before) for a client that must keep a single
   budget.
4. Look at every non-GET call: is it [safe to repeat](transient-retries.md#idempotency)? It is not
   retried until you say so.

## From hand-written Polly policies

Older code often has `AddPolicyHandler(HttpPolicyExtensions.HandleTransientHttpError().WaitAndRetryAsync(…))`
or a `DelegatingHandler` with a loop.

| You had | Here |
|---|---|
| `HandleTransientHttpError()` (5xx, 408, `HttpRequestException`) | the default transient predicate, plus attempt timeouts |
| `.OrResult(r => r.StatusCode == TooManyRequests)` in the same retry | remove it: 429 has its own [throttle retry](throttling-and-retry-after.md) that honours `Retry-After` |
| `WaitAndRetryAsync(3, n => TimeSpan.FromSeconds(Math.Pow(2, n)))` | `TransientRetry` with `Exponential` backoff, `BaseDelay` 2 s |
| `Policy.TimeoutAsync(10)` inside the retry | `AttemptTimeout` |
| `Policy.TimeoutAsync(60)` outside the retry | `TotalTimeout` |
| `.OrResult(r => r.StatusCode == NotFound)` | `AdditionalPredicate` |
| `onRetry: (_, _, _, ctx) => tokenCache.Clear()` | `OnRetry`, see [retrying with a fresh token](transient-retries.md#retrying-with-a-fresh-token) |
| a breaker policy | keep a breaker, but put it in the right place: see [layered retries](layered-retries.md) |

**Exception predicates.** Clients generated by libraries such as Refit or NSwag wrap failures in
their own exception types. The pipeline sees the raw `HttpRequestException` *before* that wrapping, so a
predicate on the library's exception type never fires. If you had one, check what the handler actually
sees, and walk `InnerException` when you need to look inside:

```csharp
options.TransientRetry.AdditionalPredicate = outcome =>
{
    for (var e = outcome.Exception; e is not null; e = e.InnerException)
    {
        if (e is IOException) return true;
    }

    return false;
};
```

**Handler order.** A policy handler added after an auth handler did not re-run the auth handler on
retry. Here the pipeline also runs where you add it. Call `AddHttpResilience` *first*, before the token
handler, so the pipeline is outermost and each attempt gets a fresh token — see
[where the handler sits](architecture.md#where-the-handler-sits).

## From `AddStandardResilienceHandler`

The standard handler is a good start, but its defaults suit a different workload: an interactive
request that must answer in seconds.

| | Standard handler | This pipeline |
|---|---|---|
| Total timeout | 30 s | computed from the retries (525 s with defaults), or set |
| Attempt timeout | 10 s | 30 s |
| Retries | 3, for 5xx, 408, **429** and exceptions, in one budget | transient and 429 each have their own budget |
| Non-idempotent methods | retried | not retried unless marked safe |
| `Retry-After` | honoured, but inside the 30 s total | honoured, up to `MaxRetryAfter` |
| Circuit breaker | per client, per instance: opens at 10% failures | none — use a [shared breaker](https://github.com/iverburgh/azure-functions-circuit-breaker-playbook) |
| Rate limiter | concurrency 1,000, per handler | per dependency, shared by every client, optionally across instances |
| `HttpClient.Timeout` | unchanged (100 s) | set to infinite; the pipeline owns time |

What usually breaks with the standard handler in a background worker:

- a `Retry-After: 60` never gets a chance inside a 30-second total timeout;
- a `POST` that timed out on the client but succeeded on the server is sent again;
- the built-in breaker opens on one instance after a burst of 429s and starts failing calls that would
  have succeeded, while the other instances keep calling.

To switch:

1. Remove `AddStandardResilienceHandler()` from the client. Check `ConfigureHttpClientDefaults` too: a
   standard handler added there applies to *every* client and stacks with this one. Recent versions of
   `Microsoft.Extensions.Http.Resilience` have `RemoveAllResilienceHandlers()` for exactly this.
2. Add `.AddHttpResilience()`.
3. Port `options.Retry.ShouldHandle` customisations to `AdditionalPredicate` — 429 is no longer yours to
   handle.
4. Port `options.Retry.OnRetry` to `TransientRetry.OnRetry`.
5. If you relied on the 30-second budget, set `TotalTimeout = 00:00:30` and lower `MaxRetryAfter` to fit.
6. Decide where breaking belongs: per dependency and shared, not per client instance.

The [circuit breaker playbook](https://github.com/iverburgh/azure-functions-circuit-breaker-playbook/blob/main/docs/timeouts-and-retries.md)
explains why the standard handler's breaker and a shared breaker do not mix.

## A client that only needs throttling

Some clients must keep their own timeout and retry behaviour — a long-running upload, or code that
already retries at a higher level. Give them [`AddOutboundThrottling`](timeouts.md#the-throttling-only-pipeline)
instead: they still respect the shared rate limits and 429 blocks, and nothing else changes.

## Rolling out

- Move one client at a time, starting with the one that hurts most.
- Watch [`resilience.http.throttle.requests`](observability.md#metrics) and the retry delays for a
  week before the next.
- Add rate-limit rules last, with a `PermitLimit` above today's peak, then lower it.
